# 设计方案

> 面向开发者与评审：说明数据模型、事务纪律、分类机制与关键取舍。
> 版本对应当前 `cn.levanll.inventory` 1.0.0。

---

## 一、设计基线

| 项 | 取值 | 说明 |
|---|---|---|
| 平台 | Android 7.0+（minSdk 24） | 目标机含 HarmonyOS 4.x（Android 12 底座）等无 GMS 设备 |
| 语言 | Kotlin 1.9.24 | 协程用于事务与 IO 调度 |
| UI | Jetpack Compose（BOM 2024.06） | 声明式，状态与表单同步成本低 |
| 数据 | Room 2.6.1（SQLite） | 编译期校验 SQL，支持递归 CTE 与迁移 |
| 扫码 | ZXing 3.5.3 + CameraX 1.3.4 | **不依赖 GMS / ML Kit** |
| 权限 | 相机 + 网络 | 无存储、定位、通知、通讯录权限 |

### 三条硬原则

1. **离线优先**：所有核心功能不依赖网络。联网仅用于条码查商品信息，失败不影响任何流程
2. **数据可审计**：流水只增不删，撤销写补偿记录，历史行数值永不修改
3. **分类数据驱动**：分类条由 SQL 统计生成，不在界面写死任何分类名

## 二、数据模型

### 表结构

| 表 | 职责 | 关键约束 |
|---|---|---|
| `item` | 商品 | `barcode` 索引；`deleted_at` 软删；保质期三字段 |
| `stock_record` | 流水（只增） | `reverted_by` 指向补偿记录；外键 `item_id` |
| `category` | 分类树 | `UNIQUE(name, parent_id)`；`depth` 冗余字段 |
| `category_rule` | 名称→分类规则 | `token` 唯一；`source` 区分 system/learned |
| `barcode_memo` | 条码自学习 | `barcode` 唯一；负缓存命中计数 |
| `form_memo` | 表单记忆 | key-value |

### 为何这样设计

**`depth` 冗余而非递归查询**：三级分类树最多三层，`depth` 让「只取一级」这类查询变成 `WHERE depth = 1`，避免每次展开树。

**`barcode_memo` 独立于 `item`**：条码与商品的映射不能只存在 `item` 表。商品可被删除、可数量归零，但「这个条码对应什么商品」的知识应当保留，否则用户每次都要重新填。

**保质期不落过期时间**：只存 `production_date` 与 `shelf_life_days`，到期时间由 SQL 现算。若落库，修改保质期时必须同步更新到期日，两处不一致会产生难以排查的 bug。

## 三、事务纪律

### 串行化

Room 的 `withTransaction()` 在本项目里是**唯一写入口**。所有写操作（入库、加减、撤销、分类变更、条码记忆）都包在事务内：

```kotlin
db.withTransaction {
    // 校验 → 写 item → 写 record
}
```

任一环节抛异常，整体回滚。这是「批量操作不允许半成功」的实现基础。

### 撤销的补偿式设计

`stock_record` 是只增表。撤销不是删除或修改历史行，而是：

1. 插入一条反向记录（`delta` 取反，`reason = 'REVERT'`）
2. 把原记录的 `reverted_by` 指向新记录 id

```
id=1  IN  +3   before=0  after=3   reverted_by=2
id=2  OUT -3   before=3  after=0   reason=REVERT
```

好处：
- 历史完全可追溯，任何时刻都能还原「当时发生了什么」
- 月度统计天然正确——撤销出库 = 出库后又补回，消耗被抵消
- 无并发风险——补偿是插入，不是更新

### 入库三分支

| 分支 | 触发条件 | 行为 |
|---|---|---|
| 追加 | `existingItemId != null` | 累加到已有商品，锁定规格与单位 |
| 新建 | 默认 | 同名同规格不存在时直接建 |
| 冲突 | 同名同规格且 `quantity > 0` | 抛 `DUPLICATE_ITEM`，由 UI 让用户二选一 |
| 复活 | 同名同规格但 `quantity <= 0` | 直接复用旧条目，避免重复行堆积 |

「复活」分支容易被忽略但很重要：用户把商品减到 0 删掉后，下次入库同名商品若不复用，数据库会积累大量同名空行。

## 四、分类机制

### 三级树的存储与排序

分类用 `parent_id` 自关联，`depth` 标记层级（1/2/3）。

**排序是这里最容易出错的地方**。`sort` 值设计为 `10, 11, 12, 20, 21...`，若直接 `ORDER BY sort`：

```
服装(10) → 上装(11) → 下装(12) → 食品(20) → 生鲜(21)   ← 层级错乱
```

正确做法是递归 CTE 生成路径串：

```sql
WITH RECURSIVE tree(id, name, path) AS (
    SELECT id, name, printf('%05d', sort) || '/' || name
    FROM category WHERE parent_id IS NULL
    UNION ALL
    SELECT c.id, c.name, tree.path || '/' || printf('%05d', c.sort) || '/' || c.name
    FROM category c JOIN tree ON c.parent_id = tree.id
)
SELECT * FROM tree ORDER BY path ASC
```

路径串 `00010服装/00011上装/00111T恤` 的字典序天然等于先序 DFS，无需在代码里排序。

`printf('%05d')` 的零填充是关键——否则 `sort=100` 会排在 `sort=20` 之前。

### 名称识别

```
名称 → 中文 n-gram 切词（整串 + 2~4 字，上限 24）
     → 命中 category_rule
     → 加权：weight × 长度加成(≥3字 ×1.2) × 学习加成(learned ×1.3) × 深度加成
     → 归一化：命中权重和 / token 数，封顶 0.9
     → 分档：≥0.75 自动采用 / 0.40~0.75 需确认 / <0.40 留空
```

**不用分词库**：中文商品名普遍短（3-8 字），n-gram 对「蒙牛全脂牛奶」这类复合名足够，且零依赖、可离线、行为确定。

**深度加成**：三级分类比一级更具体，同样命中时优先三级。「精华」指向「美妆个护/护肤/精华」比指向「美妆个护」更有用。

### 人工校正即学习

用户改选分类时，把名称切词写入 `category_rule`（`source = 'learned'`，权重 +0.2，封顶 3.0）。下次同名词自动命中。

这是**唯一的学习通道**，不需要模型、不需要服务端。

## 五、保质期与排序

### 排序的三级键

```sql
ORDER BY
  c1.sort, c2.sort, c3.sort,    -- 1. 分类树分组
  has_expiry ASC,                -- 2. 组内有保质期优先
  expiry_at ASC,                 -- 3. 按到期时间升序（已过期为过去时间，排最前）
```

**为什么分类必须是第一键**：早期版本把保质期放在首位，结果一份快过期的牛奶跑到整个列表最顶端，把「T恤」分组的商品拆散在两处。用户找东西时反而更慢。

正确的语义是：**同分类的商品永远相邻，组内再按紧急度排**。

### 状态分档

| 剩余天数 | 状态 | 配色 |
|---|---|---|
| < 0 | 已过期 | 红 |
| 0–3 | 紧急 | 红 |
| 4–7 | 临近 | 橙 |
| 8–30 | 接近 | 黄绿 |
| > 30 | 正常 | 灰 |

用徽标文字而非整行变色——整行变色会让列表变成一片红黄，反而失去警示效果。

## 六、扫码实现

### 为什么不用 ML Kit

目标设备之一是 HarmonyOS 4.2（Android 12 底座），只有 Huawei ID，无 Google 服务。ML Kit 依赖 GMS，在这些设备上不可用。

ZXing 是纯 Java 实现，无任何 Google 依赖。

### toBitmap 而非手工解析 YUV

`ImageProxy` 的 Y 平面每行实际字节数是 `rowStride`（按 16/32 对齐补齐），通常**大于**图像宽度。

早期实现按 `width` 连续读取整块缓冲区，每行错位累积，图像被斜切成垃圾数据。ZXing 在垃圾里凑出了能通过 EAN-8 校验的**假码**（真实条码 `6972046811374` 被读成 `02224020`）。

这种错误比直接失败更危险——它不报错，用户会以为扫对了。

改用 `ImageProxy.toBitmap()`，由 CameraX 处理全部平面与跨距细节。代价是每帧多一次位图分配，用 80ms 解码节流抵消。

### 条码商品查询的三级数据源

| 优先级 | 来源 | 可靠性 |
|---|---|---|
| 1 | `barcode_memo` 本地自学习 | 最高（用户亲手确认过） |
| 2 | `item.barcode` 已入库商品 | 高 |
| 3 | Open Food Facts（JSON API） | 中（欧美食品覆盖好） |
| 4 | go-upc（HTML 抓取） | 中（国产条码覆盖较好） |

**本地优先于联网**：用户自己填过的数据永远比第三方可靠。

**联网结果只作建议**：第三方数据可能错、可能过时。直接写进表单等于把错误变成用户的库存事实。

**负缓存用哨兵对象**：`ConcurrentHashMap` 不允许 null value，把「查不到」存成 null 会抛 NPE。用 `NotFound` 单例代表「确实查过、确实没有」。

## 七、关键取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 分类条是否常驻 | 只渲染 `quantity > 0` 的分类 | 空分类占位是纯噪音 |
| 归零是否自动删商品 | 不删，软删需确认 | 误删不可逆，且历史流水要能引用 |
| 出库是否单独页面 | 无，列表内 `−/+` | 最高频动作不该有跳转 |
| 盘点功能 | 已移除 | 个人场景下"逐项核对"的成本远高于收益，用随时增减替代 |
| 批量出库 | 已移除 | 与列表内加减重复，且多一层选择成本 |
| 数据导出 | 不提供 | 保持界面简洁，换机接受重新录入 |
| 云同步 | 不做 | 隐私优先，且避免后端维护成本 |
| 系统通知 | 不做 | 需要通知权限，过期提醒只在打开应用时出现 |

## 八、已知缺陷与修复记录

开发期实际遇到的问题，记录备查（详见 CHANGELOG）：

1. **ImageProxy 解析错误** → 改 `toBitmap()`
2. **排序键错误** → 分类优先，组内临期优先
3. **状态覆盖** → `refreshInventory` 用旧快照赋值，覆盖了并发写入的 `expiredOnLaunch`
4. **ConcurrentHashMap NPE** → 哨兵对象
5. **分类选择器层级错乱** → 递归 CTE 路径串排序
6. **edge-to-edge 遮挡** → 补 `statusBarsPadding()`
7. **浮层图标不可见** → 显式指定 tint
8. **R8 与部分唯一索引冲突** → 改普通索引 + 迁移重建

## 九、数据库迁移链

| 版本 | 变更 |
|---|---|
| v1 | 初版：含 `count_session` / `count_line`（盘点表） |
| v2 | 移除盘点表；`ux_item_barcode` 部分唯一索引改为普通索引 |
| v3 | 加 `depth`（三级分类）；加 `expiry_enabled` / `production_date` / `shelf_life_days` |
| v4 | 加 `barcode_memo` 表 |

迁移的注意点：

- **`DROP INDEX IF EXISTS` 要放在建表前**，否则 Room schema 校验会因未知索引失败
- **种子数据用 `seed_version` 守卫**：只在版本号变化时补缺失项，不覆盖用户改动
- **`ALTER TABLE ADD COLUMN` 必须给 NOT NULL 列默认值**，否则已有行违反约束
